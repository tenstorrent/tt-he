# tt-he — homomorphic encryption and PIR primitives on Tenstorrent

Fully homomorphic encryption (BFV) and private information retrieval (PIR) built from the ground up on
Tenstorrent Tensix cores, with **all arithmetic on device** and every kernel validated **bit-exact**
against a CPU/Python golden.

The stack is built bottom-up, each layer validated before the next:

```
modular multiply (Montgomery, SFPU)         ->  int8 modular matmul (matrix engine)
  ->  NTT / negacyclic NTT  (1024, 2048, 8192, 32768, four-step, multi-core)
  ->  RNS base conversion (approximate, exact/Shenoy-Kumaresan, CRNS)
  ->  BFV ciphertext ops: add, tensor multiply, rescale, relinearize / key-switch
  ->  full HE multiply: CKKS ct_mul (N=65536, L_Q=48, dnum=3) and BFV/CROSS Set-B (N=8192, L=8, dnum=2)
  ->  OnionPIR-style PIR pipeline (65 536 rows, end-to-end demo)
  ->  an HE compiler: op graph -> schedule -> generated device code  (compiler)
```

## Results

Measured on a **Blackhole p150**, all bit-exact against the goldens:

| workload | configuration | result |
|---|---|---|
| **CKKS `ct_mul`** (N=65536, `L_Q`=48, dnum=3) | G=130, traced; NTT fused into one dispatch, base conversion on the matrix engine | **24.07 ms/op** device-busy, 41.57 ms host wall, `0/6029312`, and `decode(decrypt(out))` correct to **39.0 bits** |
| **HE multiply** (CROSS Set-B, N=8192, L=8, dnum=2) | 64 cores, traced-resident | **24.4 ms/mul** host wall, **14.1 ms** device-busy span, `device-vs-oracle 0/114688` |
| **negacyclic NTT-8192** (`nntt8192_mc`) | 32 / 64 cores | **80.8 µs** / **68.9 µs**, `0/8192` mismatches |
| **32×32 modular matmul** via int8 matrix engine | 1 core | `0/1024` mismatches |
| **vector modular multiply** (Montgomery, SFPU) | 1 core, N=4096, host otherwise idle | 17.1–17.9 µs/iter ≈ **228–240 M modmul/s**, `0/4096` mismatches |

Reproduce the headline number with `sh tools/bench/ckks_ctmul.sh`; the full suite with `sh tools/run_all.sh`.
The Set-B row is `sh tools/bench/hemul_cross.sh` — a different, smaller ring, kept because it is
CROSS's published Table VIII parameter set (`docs/he/cross_comparison.md`).

> **These are device figures, and the host matters.** On a loaded machine (load average ~5) the
> single-core modmul above measured 44.9–48.1 µs — about 2.6× its idle figure — while still
> returning `0/4096`. Correctness never moves; timings do. Measure on an otherwise idle host, per
> [`docs/guide/profiling.md`](docs/guide/profiling.md).

> Historical results on Wormhole **n150** are in `docs/he/` and `docs/matmul/`. Those numbers were taken
> on a different architecture *and* an earlier code state, so do not compare them directly with the table
> above — see `docs/he/blackhole_port.md` §3 for why.

## Prerequisites

| # | requirement | needed for | notes |
|---|---|---|---|
| 1 | **an installed tt-metalium prefix** | build **and** run | *installed*, not a build tree — see below |
| 2 | C++20 compiler, CMake ≥ 3.22 | build | |
| 3 | Python 3.10+ with numpy | goldens / reference models | `conda env create -f environment.yml` (or `requirements.txt`) — not needed for device work |
| 4 | a Tenstorrent device, free | running anything on device | one device program at a time |

**"Installed" means an install *prefix*, anywhere — not necessarily system-wide.** A private directory
such as `~/work/ttm-install` works exactly as well as `/usr/local`, needs no root, and keeps SDK
versions isolated.

**A tt-metal *build tree* is not usable.** `find_package(TT-Metalium)` needs `Metalium.cmake`, which is
generated by `cmake --install` and does not exist in `build_Release`. `setup.sh`, `env.sh` and CMake all
detect this specific case and say so. If you have only built tt-metal, turn that into an install prefix:

```bash
sh tools/install_ttmetalium.sh -s /path/to/tt-metal        # -> $HOME/work/ttm-install
sh tools/install_ttmetalium.sh -s /path/to/tt-metal -p /usr/local -S   # system-wide (sudo)
```

**Python (only for the reference models — device work needs none of it).** Conda is the recommended
path; the repo takes the interpreter from one config key, so there is nothing to remember to activate:

```bash
conda env create -f environment.yml && conda activate tt-he
echo "PYTHON=$(which python)" >> config.local.env
```

pip users: `requirements.txt`. Note that on Ubuntu 24.04+ the system Python is PEP 668
externally-managed, so a plain `pip install` is refused — use conda, `pip install --user`, or
`apt install python3-numpy`.

Validated against tt-metalium **`v0.76.0-dev20260728`**. tt-metal moves fast; a much newer SDK may need
small source fixes (moved headers, renamed APIs).

## Quick start

```bash
sh tools/setup.sh        # finds your tt-metalium install, writes config.local.env, checks everything
                         # if it cannot, it prints exactly what to fix

. env.sh                 # exports the 4 required env vars from that config
cmake -B build -G Ninja
cmake --build build -j                      # or: --target ckks_ctmul

sh tools/run_all.sh                         # the 85 device tests that need no missing fixture
ctest --test-dir build -L '^nohw$'          # host-only tests (no device needed)

./build/vector_modmul                       # smallest single check
./build/he_demo 6 7                         # HE add + multiply, on device
sh tools/bench/ckks_ctmul.sh                # THE benchmark: the best CKKS ct_mul
sh tools/bench/hemul_cross.sh               # the older Set-B HE-multiply harness
```

Check an existing setup at any time with `sh tools/doctor.sh` — it verifies each prerequisite and, for
anything missing, prints the command that fixes it.

**One config file is the only thing a new machine needs.** `config.local.env` (written by `setup.sh`,
gitignored) declares where tt-metalium is; `config.defaults.env` documents every key. Both `env.sh` and
CMake read them, so `cmake` works whether or not you sourced anything first, and there is no second
place to keep in sync. Precedence: environment → `config.local.env` → `config.defaults.env` →
autodetect (`/usr/local`, `$HOME/work/ttm-install`, `../ttm-install`).

`env.sh` owns `TT_METAL_HOME`, `TT_METAL_RUNTIME_ROOT`, `CMAKE_PREFIX_PATH` and `LD_LIBRARY_PATH` —
never set them by hand. `TT_METAL_HOME` matters at **run** time as well as build time: kernels are
JIT-compiled when a program runs, using the compiler inside `libexec/tt-metalium`.

**If a run hangs**, the device is likely wedged from an earlier crashed run — `tt-smi -r`, then retry.
Until you reset, the *next* program will also hang even though nothing is wrong with it.

## Options

Most programs here are driven by environment variables rather than flags, because an experiment's arms
have to be selectable without recompiling. The ones worth knowing:

| variable | effect |
|---|---|
| `HE_ITERS=N` | replay iterations for the traced HE/CKKS runs (default 20) |
| `NTT_CORES=4\|8\|16\|64` | Tensix cores per `ct_mul` — fewer dispatches as it rises; the workload is dispatch-bound |
| `TT_METAL_DEVICE_PROFILER=1` | capture a device trace; `tools/traces/` analyses the CSV it drops in `generated/traces/` |
| `TG18NTT_FUSE=1 TG18NTT_FBC=fpu` | the benchmark's published arm — already pinned by `ckks_ctmul`, listed here because `exp_tg018ntt` selects the other rungs the same way |
| `TB001B_GEN=<path>`, `TG000_GEN=<path>` | regenerate an experiment's case file instead of reading it (those two fixtures are not committed) |
| `PIR_GEN=<script>` | the generator `pir_demo` uses to build its case |
| `PYTHON=<path>` | in `config.local.env` — which interpreter the reference models use |

Tests are selected by ctest label, one per kind of program:

```bash
ctest --test-dir build -L '^hw$' -LE '^fixture$'   # 85 — the correctness gate
ctest --test-dir build -L '^perf$'                # 1  — the published benchmark
ctest --test-dir build -L '^study$'                # 25 — finished experiments
ctest --test-dir build -L '^nohw$'                 # 5  — host-only, no card needed
```

## Troubleshooting

| symptom | cause and fix |
|---|---|
| a run hangs with no output | the card is wedged from an earlier crash, or another program holds it — one device program at a time. `tt-smi -r`, then retry |
| `cannot open case file …` | a fixture that is not committed. The message names the command that rebuilds it |
| JIT errors after moving files | kernel paths are runtime strings, so a stale **binary** keeps the old path. Rebuild everything, not just the target you touched |
| a doc points at a file that moved | `ctest -L nohw` runs `tools/check/links.sh` and `tools/check/paths.sh`, which catch exactly this |

`sh tools/doctor.sh` checks every prerequisite and prints the command that fixes whatever is missing.
Deeper device debugging — watcher, profiler, common failure modes — is in
[`docs/debugging.md`](docs/debugging.md).

## Repository map

`kernels/` is the only **device** code — Tensix compute and dataflow kernels, JIT-compiled by the
SFPI/RISC-V toolchain when a program runs. `host/` is the only **host** C++, compiled once by your
system compiler. Scripts live in `tools/`, data and goldens in `reference/`, so neither tree holds
anything but source.

| path | contents |
|---|---|
| `CMakeLists.txt` | every target, one line each via `cmake/HeDeviceTarget.cmake` |
| `kernels/` | Tensix compute + dataflow kernels — the core of the project: `shared/` is the validated tree, `experiments/` the per-experiment trees, `ir/` the compiler path |
| `host/` | **all host C++, and nothing else** — one subfolder per kind of program (below) |
| `host/lib/` | the reusable surface. `he_api` (BFV/CKKS ops) · `pir_engine2048` — the PIR engine the 65 536-row demo and 17 tests run on · `pir_demo_api` — the small OnionPIR façade behind `pir_demo`, and its only consumer |
| `host/examples/` | `he_demo`, `pir_demo` — start here to see it work |
| `host/tests/` | correctness suite by subsystem (`vector/ matmul/ ntt/ baseconv/ he/ pir/ ir/ common/`) — label `hw`, must always pass |
| `host/benchmarks/` | **the** benchmark: `ckks_ctmul`, the best CKKS `ct_mul` — label `perf`, and the only program under it |
| `host/experiments/` | the `exp_*` studies; each answered a question and its conclusion is in `docs/`. `legacy/` holds the older non-`exp_` programs — kept, but no longer the benchmark — label `study` |
| `compiler/` | the HE compiler: op graph → schedule → generated device code; `he_compile.py` plus its `configs/` and `programs/` |
| `reference/` | goldens, one directory per subsystem (`he/ pir/ ntt/ ntt_matmul/ matmul/ ir/ vector/`): the Python reference model, the `gen_*.py` generators, and the committed `.bin` case files, all in the same directory per subsystem |
| `tools/` | entry points at the top (`setup.sh`, `doctor.sh`, `install_ttmetalium.sh`, `run_all.sh`, `gen_fixtures.sh`), then `bench/` — the benchmark and sweep runners · `check/` — the three repo-consistency checks, run as `nohw` ctest tests · `traces/` — device-profiler analyzers · `pir_ui/` — the PIR demo browser UI |
| `docs/` | design docs and performance reports per subsystem — start at `docs/README.md`. `guide/` is the normative pair (how to measure, how to optimise) |

Start at `docs/README.md` for the documentation index, `docs/he/README.md` for the BFV evaluator, and
`docs/he/blackhole_port.md` for build/env setup and the Blackhole port.

## Support matrix

| architecture | status |
|---|---|
| Blackhole **p150** | **verified.** Full sweep 2026-08-03: all binaries pass, bit-exact. Since then the tree was restructured — paths only, no arithmetic changed — and the affected tests were re-run per change rather than as one sweep (see below) |
| Wormhole **n150** | previously verified; **not** re-tested since the Blackhole port |

There are now **119 executables / 120 ctest tests** (the "77" of the August sweep predates later
experiments). The restructuring since that sweep moved files and rewrote paths; each step was verified
by rebuilding everything and re-running the tests it could plausibly break — the fixture readers, the
kernel-prefix consumers, the HE and PIR groups, `ckks_ctmul`, and the `nohw` tier. **The full sweep has
not been repeated**, so if you need a single green record, run it:

```bash
sh tools/bench/baseline_sweep.sh out.txt      # ~1 hour, needs the card free
diff out.txt .baselines/baseline_all_green.txt
```

CI runs the hardware-free checks on every push: every `.sh` through `dash -n`, `compileall` over
`reference/` and `compiler/`, a host-only configure and build, then `ctest -L nohw` — which is where
the three repo-consistency checks live (`tools/check/{links,paths,divergence}.sh`). The device suite
is a self-hosted, opt-in job running `-L '^(hw|perf)$'` — see `.github/workflows/ci.yml`.

## Contributing

Bugs go to **GitHub Issues**; fixes and new functionality go to **Pull Requests**. Pull requests are
reviewed **weekly**. See [CONTRIBUTING.md](CONTRIBUTING.md) for the full process and
[CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) for the Contributor Covenant this project follows.

Two project-specific requirements, because they are what keeps the numbers in this README meaningful:

- **A change that touches arithmetic must stay bit-exact against the golden.** Every kernel here is
  validated against a CPU/Python reference in `reference/`; a PR that changes one shows the mismatch
  count (`0/N`) from the affected test.
- **A performance claim must be measured the way [`docs/guide/profiling.md`](docs/guide/profiling.md)
  says**, on the hardware named. A number produced outside those rules is not quotable — that document
  is normative, not advisory.

Security vulnerabilities: see [SECURITY.md](SECURITY.md). Do not open a public issue for them.
