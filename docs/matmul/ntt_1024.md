## 1. What this is and why we need it

The **NTT** is the DFT done in a prime field `Z_q` instead of the complex numbers — it turns a
length-`N` polynomial multiply (the core of FHE) from `O(N²)` into `O(N log N)`. Every FHE
ciphertext operation reduces to polynomial multiplies mod `q`, and the NTT is how those are made
fast. This document covers the **size-1024** transform: `X[j] = Σ_n x[n]·ω^{nj} mod q`, where `ω`
is a primitive 1024-th root of unity mod `q`.

The point of this doc is that the 1024-NTT is **not a new kernel** — it is the **composition of
the two primitives already documented**:

- the **modular matrix multiply** (`docs/matmul/modular_matmul_overview.md`), used twice, and
- the **element-wise modular multiply** (`docs/vector/modular_multiplication.md`), used
  once as the twiddle stage.

So the 1024-NTT is the first place those two foundations come together into a real FHE building
block, end-to-end on the device.

Target field: `q = 167772161 = 5·2²⁵+1`, the NTT-friendly 28-bit prime (it has the 2-power
structure NTT needs, and it sits near 2²⁸ where the radix-128 lowering and the recombine bounds
hold — see §6).

## 2. The algorithm — the four-step (32×32) NTT

Computing a 1024-point transform as one matrix would be a 1024×1024 mod-q matmul. Instead we
use the classic **four-step** factorization with `N = 32 × 32`, which turns it into **two
32×32 matmuls plus one element-wise twiddle** — sizes that map directly onto the 32×32 tile.

Index the input `n = n₁ + 32·n₂` and the output `j = j₂ + 32·j₁`, and reshape `x` into a 32×32
matrix `Xin[n₂,n₁] = x[n₁ + 32·n₂]`. Using `ω¹⁰²⁴ = 1` and `ω³² = ω₃₂` (a primitive 32-nd root),
the transform factors exactly into:

```
A.  G  = W · Xin          column DFTs:  G[j₂,n₁] = Σ_{n₂} W[j₂,n₂]·Xin[n₂,n₁]   (W[a,b]=ω₃₂^{ab})
B.  G' = G ⊙ T            twiddle:      G'[j₂,n₁] = G[j₂,n₁]·ω^{j₂·n₁}
C.  H  = G' · W           row DFTs:     H[j₂,j₁] = Σ_{n₁} G'[j₂,n₁]·W[n₁,j₁]
    X[j₂ + 32·j₁] = H[j₂,j₁]            output reindex
```

`W` is the 32-point DFT matrix mod `q`; `T[a,b] = ω^{ab}` are the twiddle factors. Steps A and C
are **32×32 modular matmuls**; step B is an **element-wise modular multiply** of two 32×32 tiles.
That is the whole transform — three mod-q operations on 32×32 tiles, plus an index permutation
done on the single output read.

## 3. How it maps onto the two primitives

```
 x (1024) ─reshape→ Xin[32×32]
      │
      A:  G  = W · Xin        ── modular MATMUL  (decompose → int8 matmul → recombine)
      │
      B:  G' = G ⊙ T          ── vector MODMUL   (element-wise (a·b) mod q)
      │
      C:  H  = G' · W         ── modular MATMUL  (decompose → int8 matmul → recombine)
      │
 X (1024) ←reindex── H[32×32]
```

Each matmul stage is exactly the lowering from the matmul overview: decompose the dynamic operand
into radix-128 limbs, run the int8 matrix engine, recombine + reduce mod `q` on the SFPU. The
twiddle stage is exactly the Montgomery modmul from the vector overview.

**The fold trick (no runtime fold multiply).** A naive radix-128 matmul would need a `mod q`
multiply to fold the `128^p` limb weights into one operand at runtime. Instead, because `W` is a
**constant** (the DFT matrix, known offline), the limb-weight fold is **baked into `W`** during
host precompute:
- stage A: `WfoldA[p,r] = limb_p(128^r · W mod q)` — `W` is the matmul LHS,
- stage C: `Wrhs[p,r] = limb_r(128^p · W mod q)` — `W` is the matmul RHS.

So at runtime there is **no fold modmul** in either matmul — only the dynamic operand is decomposed
(plain shifts/masks), and the twiddle `T` is pre-converted to Montgomery form once. The transform's
only runtime reductions are the two recombines and the one twiddle modmul.

## 4. Implementation — fully on-device, fused

Program: `tests/ntt/ntt1024_dev.cpp`, single Tensix core. The host writes the input + baked constants
(`WfoldA`, `Wrhs`, Montgomery twiddles) **once**, issues the stages, and reads the result **once** —
**no host↔device traffic and no host arithmetic between stages.** The output index permutation is
folded into that single readback.

The transform is **three chained device programs**:

| stage | program | what runs |
|---|---|---|
| **A** | fused modular matmul | decompose(Xin) → int8 matmul(WfoldA) → recombine → `G` |
| **B** | twiddle modmul | `G' = G ⊙ T` (element-wise Montgomery) |
| **C** | fused modular matmul | decompose(G') → int8 matmul(Wrhs) → recombine → `H` |

Stages A and C are each a **single fused kernel** (`kernels/shared/compute/fused_matmul_{a,c}.cpp`): the
int8 limb tiles and int32 plane tiles stay **L1-resident** across decompose → matmul → recombine —
no DRAM round-trip and one dispatch per matmul, instead of three. Within one kernel the engine is
switched SFPU → matrix → SFPU at each phase boundary. (Earlier versions ran 7–8 separate programs
chained through DRAM; see the per-stage docs below.)

> **Do not switch engines with a full re-init.** `unary_op_init_common` / `mm_init` both re-run the
> DEST-sync handshake (`llk_math_pack_sync_init` + `llk_pack_dest_init`); re-running it mid-kernel
> deadlocks MATH against PACK (hangs every NTT binary on Blackhole; latent on Wormhole). Use one full
> init at kernel entry, then `matmul_init` + `reconfig_data_format*` / `pack_reconfig_data_format`.
> Full diagnosis: [../he/blackhole_port.md](../he/blackhole_port.md) §2.

The reduction work is on the **32-bit SFPU** in SFPI register passes (the recombine's Montgomery
`mod q` and the twiddle modmul), the multiply-accumulate is on the **8-bit matrix engine** — the
same two-engine split as the matmul overview, now spanning a whole transform.

## 5. Performance

**~95.5 µs / NTT-1024** on one Tensix core (n150), bit-exact throughout — 1.54× faster than the
first fully on-device version, and ~12× faster than the original host-orchestrated one.

The full progression, the per-stage breakdown, the 4-core matmul variant and the "why the modular
reduction dominates, not the matmul" analysis are in **[`ntt_1024_perf.md`](ntt_1024_perf.md)**.
One doc owns these numbers so they cannot drift apart.

## 5.1 Multi-core variant (`tests/ntt/ntt1024_dev_mc.cpp`)

The plane-matmul produces 4 independent int32 result planes, so each gets its own Tensix core:

```
core oi:  C_oi = sum_k a_k @ b_k     (NB int8 matmuls accumulated locally)
          write C_oi -> DRAM tile oi
```

All 4 cores run one program (`CoreRange {0,0}..{3,0}`) with per-core runtime args, reading operands
from shared DRAM constants; a single core then gathers the 4 planes and recombines them
(`recombine_compute.cpp`, unchanged). Kernels: `compute/matmul_plane.cpp`,
`dataflow/reader_matmul_mc.cpp`. Bit-exact (`0/1024`, seeds 0/1/7/42).

**It buys ~8%, and that is the point.** The matmul stage drops only ~14 → ~12.5 µs, not ~4×,
because at single-tile sizes a matmul stage is dominated by dispatch + CB/NOC overhead rather than
the FPU — and the three Montgomery reductions, which are ~75% of the transform, are still
single-core. The 4-core layout is the right shape for larger M/N/K, where the matmul does dominate.
Full design detail: [`history/NTT_1024_MULTICORE.md`](history/NTT_1024_MULTICORE.md).

## 6. The prime constraint

`q` must satisfy three things at once, which is why `167772161` is the canonical choice:

1. **NTT-friendly:** `1024 | (q−1)` (and `32 | (q−1)`), so the required roots of unity exist.
   `167772161 = 5·2²⁵+1` has `q−1 = 5·2²⁵`. ✓
2. **`q < 2²⁸`:** so every value splits into exactly four 7-bit limbs for the int8 matmul
   (radix-128), shared with the matmul overview. ✓
3. **Near 2²⁸:** the recombine's lazy reduction is currently tuned for `q ≈ 2²⁸` (`low < 1.61q`).
   Smaller NTT-friendly primes (26/27-bit) run the *same* pipeline but need the dual-Montgomery
   recombine (reduce the low half too) — a localized, prime-agnostic fix.

So a small NTT-friendly prime like `12289` is valid for the *transform math* but currently fails
the recombine bound; the fix is scoped (see the matmul overview §10 caveats).

## 7. Where this fits / scaling

- **Multi-core:** `tests/ntt/ntt1024_dev_mc.cpp` splits the int8 plane-matmul across 4 cores (one
  output plane per core) — see `history/NTT_1024_MULTICORE.md`.
- **Larger transforms:** the same factorization generalizes — `tests/ntt/ntt32768_dev.cpp` does a
  `32×32×32` three-factor 32768-point NTT, reusing the identical matmul + twiddle + recombine
  machinery.
- This 1024-NTT is the proving ground: it shows the modmul and modular-matmul primitives compose
  into a complete FHE transform end-to-end on device, and it's where the fusion / SFPI / two-engine
  decisions pay off at the workload level.
